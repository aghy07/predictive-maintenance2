# ML pipeline and validation

## Dataset and target

`ml/data/machine_sensor_history.csv` is generated by `ml/generate_data.py`. It contains 1,800 synthetic independent rows (1,513 normal, 287 failure; 15.94% failure prevalence), not observations from a factory. The generator uses seed 42 and samples five sensor values, then derives probabilistic failure labels from a latent weighted rule:

- temperature above 85 °C: 0.55
- vibration above 7.5 mm/s: 0.85
- pressure above 130 bar: 0.70
- load above 85%: 0.75
- power above 80 kW: 0.45

The sum is clipped at 1.0 and used as the probability for the generated binary `failure` target. The columns `temperature_c`, `vibration_mm_s`, `pressure_bar`, `load_percent`, and `power_kw` are the only predictors. The target is not included as a feature. This is an educational synthetic relationship, not a physically validated failure mechanism; there are no real machine IDs or time-series groups from which to claim temporal or machine-level generalization.

## Leakage controls and model comparison

`ml/train_model.py` validates the dataset and performs a stratified 80/20 split (`random_state=42`) before fitting any preprocessing. Median imputation is part of each candidate's scikit-learn `Pipeline`; Logistic Regression additionally scales inside its pipeline. The pipelines are cloned and fit independently within each of five shuffled stratified folds on the 80% training partition. The untouched 20% holdout is evaluated after model and threshold selection logic is fixed.

There is no oversampling, target-derived input column, preprocessing fit on the holdout, or train/test row reuse. The labels are generated from input features by design; that synthetic relationship is not an accidental target leak. The data has no group or time key, so ordinary stratification cannot measure cross-machine or future-time generalization.

All candidates use the same split and fold plan:

| Model | CV accuracy | CV failure precision | CV failure recall | CV failure F1 | CV ROC-AUC | CV PR-AUC |
|---|---:|---:|---:|---:|---:|---:|
| Logistic Regression | 0.7042 ± 0.0266 | 0.3148 ± 0.0291 | 0.7174 ± 0.0435 | 0.4374 ± 0.0353 | 0.7803 ± 0.0308 | 0.4563 ± 0.0631 |
| Random Forest | 0.9285 ± 0.0129 | 0.7569 ± 0.0464 | 0.8174 ± 0.0403 | 0.7852 ± 0.0363 | 0.9683 ± 0.0117 | 0.8009 ± 0.0690 |
| Gradient Boosting | 0.9243 ± 0.0127 | 0.7440 ± 0.0415 | 0.8043 ± 0.0496 | 0.7723 ± 0.0387 | 0.9651 ± 0.0185 | 0.8202 ± 0.0553 |

Means and population standard deviations are computed across the five training folds at the default 0.5 binary cutoff. Random Forest is selected by the predeclared training-CV ordering of failure recall, then F1, then PR-AUC. Its recall/F1 are slightly higher than Gradient Boosting in CV; Gradient Boosting has the higher mean PR-AUC, so this is a trade-off rather than a claim that one estimator dominates every metric.

## Held-out evaluation

The stored v2.0 Random Forest has the following metrics on the 360-row holdout:

| Alert cutoff | Accuracy | Failure precision | Failure recall | Failure F1 | ROC-AUC | PR-AUC | TN | FP | FN | TP |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.50 default | 0.9333 | 0.7391 | 0.8947 | 0.8095 | 0.9731 | 0.8246 | 285 | 18 | 6 | 51 |
| 0.40 selected | 0.9222 | 0.6986 | 0.8947 | 0.7846 | 0.9731 | 0.8246 | 281 | 22 | 6 | 51 |
| 0.80 comparison | 0.8750 | 0.8333 | 0.2632 | 0.4000 | 0.9731 | 0.8246 | 300 | 3 | 42 | 15 |

At the selected cutoff, the confusion matrix is `[[TN=281, FP=22], [FN=6, TP=51]]`. **FN=6** means six held-out synthetic failures were classified below the binary alert cutoff; a real system could miss a failure, so the model is not safe as the sole basis for maintenance or machine shutdown decisions.

## Alert threshold analysis

Threshold candidates from 0.25 to 0.80 are evaluated using out-of-fold training probabilities. The policy selects the highest failure recall subject to at least 0.75 cross-validated failure precision. This selected 0.40 (training OOF precision 0.7500 and recall 0.9000). Threshold selection does not use the holdout labels.

The untouched holdout shows that 0.40 and 0.50 both have six false negatives; 0.40 has four more false positives and lower precision. Thus the selected 0.40 threshold satisfied the prespecified training-CV objective but did **not** reduce holdout false negatives relative to 0.50 in this run. The threshold is an educational decision-support choice, not a proven operating optimum. The holdout should not be reused to tune and re-report a better score.

The application's four labels are separate metadata-backed bands:

| Application label | Probability |
|---|---:|
| NORMAL | below 0.40 |
| WARNING | 0.40 to below 0.60 |
| HIGH_RISK | 0.60 to below 0.80 |
| FAILURE | 0.80 and above |

The `threshold` metadata field is the 0.40 binary alert boundary and is validated to equal the `warning` risk boundary consumed by inference. The remaining risk thresholds are also read from metadata. No stored threshold is silently ignored. These application bands are not statistically optimized or calibrated risk estimates.

## Artifacts and runtime

The training command writes:

- `ml/model.joblib`: the selected fitted Random Forest pipeline (fit on the 1,440 training rows).
- `ml/model_metadata.json`: feature names/order, target, model/version, train/holdout sizes, dataset version/hash, training timestamp, five-fold comparison metrics, threshold analysis, held-out metrics, observed training ranges, and SHA-256 of the model artifact.

The API validates the metadata feature order, threshold consistency, finite observed ranges, failure class, and model file SHA-256 before loading/caching the model. Keep the two artifacts paired. Retraining changes the timestamp and hashes; deploy both files together.

The observed feature ranges stored in metadata come only from the training partition. Inputs beyond these ranges are accepted with an extrapolation warning; those ranges are not physical safety limits.

To reproduce the current artifact:

```powershell
cd ml
python generate_data.py
python train_model.py
```

Running `generate_data.py` writes only the synthetic CSV. It does not overwrite trained model metadata; `train_model.py` is the sole writer of the model artifacts.
